# OneStack v0.2 Desktop Design

Date: 2026-08-21
Status: Approved design, implementation pending

## Goal

Extend OneStack v0.1 into a hybrid desktop framework for Windows, macOS, and Linux while preserving the same application model: JSX, components, signals, Style IR, router, server/RPC primitives, and universal UI. Desktop-specific capabilities are exposed through a typed OneStack bridge rather than direct OS APIs.

## Architecture

```text
App source (TS/TSX)
  -> OneStack compiler/runtime
  -> DOM renderer / Style IR / Router
  -> Desktop WebView host
  -> Typed IPC bridge
  -> Rust native host
  -> Windows / macOS / Linux APIs
```

The main application UI is rendered in a system WebView for portability and development speed. Native capabilities and selected native UI surfaces are exposed through explicit bridge APIs. The application does not depend on Electron or Node.js APIs.

### Platform hosts

- Windows: WebView2-backed host
- macOS: WKWebView-backed host
- Linux: WebKitGTK-backed host

The host implementation is Rust. The TypeScript package is the public API.

### Window API

```ts
const settings = await window.create({
  title: "Settings",
  width: 900,
  height: 650,
  route: "/settings",
});

await settings.minimize();
await settings.maximize();
await settings.center();
await settings.setTitle("OneStack Settings");
await settings.close();
```

Supported options include resizable, fullscreen, always-on-top, transparent, frameless, decorations, and min/max dimensions.

```ts

```

Arbitrary process execution is not part of the default desktop API. A future `process.spawn` capability must use a separate explicit permission.

## Native UI escape hatch

OneStack remains hybrid, not purely WebView-only. Native-only surfaces can be exposed through:

```tsx
import { NativeTitleBar, NativeMenu, NativeFilePicker } from "@onestack/desktop/ui";
```

Each native component must provide a web fallback or fail with a clear capability diagnostic.

## IPC protocol

Protocol version: `onestack.desktop.v1`.

Request:

```json
{
  "id": "request_42",
  "namespace": "filesystem",
  "command": "readText",
  "payload": { "path": "/tmp/example.txt" }
}
```

Response:

```json
{
  "id": "request_42",
  "ok": true,
  "value": "content"
}
```

Error responses include stable codes such as `OS_DESKTOP_PERMISSION_DENIED`, `OS_DESKTOP_UNKNOWN_COMMAND`, and `OS_DESKTOP_INVALID_PAYLOAD`.

The JavaScript side does not expose unrestricted `invoke("anything")`. Public APIs map to known typed commands only.

## Permissions

Desktop capabilities are denied unless configured.

```ts
export default defineConfig({
  desktop: {
    permissions: {
      filesystem: {
        read: ["$documents", "$downloads"],
        write: ["$documents"]
      },
      clipboard: true,
      notifications: true,
      tray: true,
      shell: { externalUrls: true }
    }
  }
});
```

Permission categories:

- `filesystem.read`
- `filesystem.write`
- `clipboard.read`
- `clipboard.write`
- `notifications.show`
- `window.create`
- `window.control`
- `shell.external`
- `tray.create`
- `system.info`
- future: `process.spawn`

Native dispatch order:

```text
request
 -> schema validation
 -> known command check
 -> permission check
 -> path/domain policy check
 -> native execution
 -> serialized response
```

## CLI

```bash
onestack dev --target desktop
onestack build --target desktop
onestack preview --target desktop
onestack check
```

Desktop dev mode launches the Rust host against the OneStack/Vite development server so HMR remains available.

Desktop build flow:

```text
1. typecheck
2. OneStack compile
3. generate route/server manifests
4. build web assets
5. generate desktop/permissions manifests
6. cargo build --release
7. embed/copy web assets into desktop bundle
8. package platform artifact
```

Generated metadata:

## Updater

Updater support is opt-in and uses a signed manifest-oriented design:

```ts
const update = await updater.check();
if (update.available) {
  await updater.download();
  await updater.install();
}
```

Configuration can specify an update endpoint. Platform signing/notarization remains external to source control and is provided through release CI secrets.

## CI

GitHub Actions matrix:

```text
ubuntu-latest
windows-latest
macos-latest
```

Required checks:

- pnpm install
- unit tests
- TypeScript typecheck
- web build
- Rust `cargo check`
- desktop package smoke validation where supported

No desktop PR is merged until the shared test/typecheck/build checks and native host checks are green.

## Error handling

Stable desktop diagnostics use the `OS_DESKTOP_*` namespace. TypeScript bridge failures preserve native error codes and safe messages. Unknown native errors are normalized without leaking host internals or secrets.

## Testing

TypeScript tests cover:

- IPC request/response matching
- bridge error propagation
- permission manifest generation
- desktop configuration normalization
- native-component fallback behavior

Rust tests cover:

- permission matching
- path policy normalization
- IPC command dispatch
- payload validation

CI performs cross-platform compile checks.

## Security constraints

- No unrestricted shell execution in the default API.
- No direct access from WebView JavaScript to host internals.
- File access is constrained by configured scopes.
- External URL opening is permission-gated.
- IPC commands are enumerated and versioned.
- Signing material only enters release workflows through secrets.

## Out of scope for v0.2

- Android/iOS native renderer
- arbitrary native widget renderer for all OneStack UI primitives
- embedded custom browser engine
- bundled JS engine
- process execution enabled by default
- production cloud update service operated by OneStack

## Success criteria

v0.2 is complete when:

1. The same OneStack app can run with `onestack dev --target desktop`.
2. The desktop bridge exposes windows, filesystem, dialogs, clipboard, notifications, tray, shell, platform information, and updater foundations.
3. Permissions are generated and checked by the host.
4. The Rust host compiles on Windows, macOS, and Linux CI.
5. `onestack build --target desktop` produces the desktop build staging output and invokes the native release build pipeline.
6. Web/full-stack v0.1 behavior remains passing.
7. The v0.2 PR is merged into `main` only after CI is green.
