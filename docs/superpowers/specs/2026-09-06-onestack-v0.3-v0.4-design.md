# OneStack v0.3 + v0.4 Design

Date: 2026-09-06
Status: Approved design
Branch: `feat/onestack-v0.4`

## Goal

Extend OneStack from its current web/full-stack + hybrid desktop scope into a universal framework that also supports Android/iOS mobile applications and production-ready data, auth, storage, payments, and deployment adapters.

The guiding principle remains:

> Write the product once. Choose where it runs.

The v0.3 and v0.4 work must preserve existing v0.2 behavior for web and desktop applications while introducing optional mobile and backend-service capabilities.

---

## Scope

### v0.3

- Native-first Android/iOS runtime.
- TypeScript application/runtime layer.
- Minimal Kotlin shell for Android.
- Minimal Swift shell for iOS.
- Native primitives as the default renderer target.
- Explicit WebView fallback for unsupported or web-specific UI.
- Shared OneStack JSX, signals, routes, styles, and business logic across web, desktop, Android, and iOS.
- Capability-based mobile permissions.
- Mobile CLI build/run/release flows.

### v0.4

- Universal data API.
- Universal auth API.
- Universal storage API.
- Universal payments API.
- Deployment presets.
- Provider adapters rather than a proprietary locked backend.
- Cross-platform integration, error normalization, testing, documentation, and compatibility guarantees.

---

# v0.3 Mobile Runtime

## Architecture

The OneStack mobile runtime is TypeScript-first. OneStack application code remains authored in TypeScript/JSX and executes against a mobile renderer that converts OneStack VNodes into native mobile primitives.

The architecture is split into clear packages:

### `@onestack/mobile`

Responsibilities:

- mobile renderer
- native primitive abstraction
- lifecycle
- navigation integration
- permissions
- local device capabilities
- native bridge protocol
- explicit WebView fallback

This package is platform-neutral and contains the public mobile API.

### Android shell

A thin Kotlin host is responsible only for capabilities that require Android APIs.

Responsibilities include:

- app startup and host lifecycle
- mounting native views requested by the TypeScript renderer
- capability dispatch
- native permissions
- filesystem/device APIs
- notifications
- intents/deep links
- system UI integration

Business logic must not be duplicated in Kotlin.

### iOS shell

A thin Swift host provides the equivalent iOS bridge.

Responsibilities include:

- app startup and lifecycle
- mounting native views requested by the TypeScript renderer
- capability dispatch
- native permissions
- files/device APIs
- notifications
- deep links
- system UI integration

Business logic must not be duplicated in Swift.

## Native renderer

Native components are the default mobile output.

Initial primitive set:

- `View`
- `Text`
- `Image`
- `ScrollView`
- `Pressable`
- `TextInput`
- `Switch`
- `ActivityIndicator`
- `SafeArea`
- `WebView`

The public OneStack UI layer should expose portable components while the mobile renderer maps the relevant semantic nodes to mobile primitives.

## WebView fallback

WebView is supported only as an explicit fallback.

It must not silently replace native rendering.

Typical uses:

- third-party browser-only widgets
- complex HTML content
- functionality not yet represented by a mobile-native primitive

Unsupported portable components must surface an explicit warning or error unless the application opts into WebView rendering.

## Shared application model

The same application may reuse:

- OneStack JSX
- signals and computed state
- effects
- route definitions
- server functions
- domain/business logic
- portable styles
- service adapters

Platform-specific code must use explicit platform boundaries rather than implicit runtime checks scattered throughout application code.

## Mobile configuration

`onestack.config.ts` is extended with a `mobile` section.

Expected concepts include:

- application identifier
- display name
- app version/build number
- orientation
- permissions
- deep links / URL schemes
- splash configuration
- icons
- Android-specific overrides
- iOS-specific overrides

Platform configuration remains optional.

## Capability model

Mobile native access follows the capability pattern already used by the desktop runtime.

Examples:

- filesystem
- camera
- photo library
- microphone
- clipboard
- notifications
- location
- haptics
- sharing
- device/platform information
- external links

A native operation must not execute unless its capability is declared by the application.

Generated manifests should make permissions auditable.

## Mobile CLI

The CLI gains mobile targets:

```bash
onestack dev --target android
onestack dev --target ios

onestack build --target android
onestack build --target ios

onestack run --target android
onestack run --target ios

onestack release --target android
onestack release --target ios
```

The CLI should generate mobile manifests under `.onestack` and invoke platform tooling through a small dedicated orchestration layer.

Build output must remain deterministic and inspectable.

# v0.4 Production Service Layer

## Adapter-first design

OneStack defines stable interfaces and developer ergonomics while providers remain interchangeable.

A OneStack application must not be locked to one backend vendor merely because it uses framework APIs.

Provider-specific implementations are loaded as adapters and should remain tree-shakable.

---

## Data

Package: `@onestack/data`

Public responsibilities:

- typed queries
- insert/update/delete
- transactions
- schema definitions
- migrations
- provider-neutral errors

Initial official adapters:

- SQLite
- PostgreSQL

The core API should be small and predictable rather than attempting to reproduce every database-specific feature.

Provider-specific escape hatches may exist under adapter namespaces without contaminating the portable API.

### CLI

```bash
onestack db generate
onestack db migrate
```

Migration state must be reproducible in CI and deploy environments.

---

## Auth

Package: `@onestack/auth`

Core responsibilities:

- user identity
- sessions
- sign-in/sign-out
- email/password
- magic links
- OAuth
- route/server guards
- client session state
- adapter contracts

Auth secrets and privileged operations are server-only.

The framework must not serialize auth provider secrets into web, desktop, or mobile bundles.

Provider adapters may include Supabase-compatible or Auth.js-style integrations, but the core contract remains provider-neutral.

### CLI

```bash
onestack auth setup
```

This command should validate configuration and create framework-owned scaffolding without silently overwriting user files.

---

## Storage

Package: `@onestack/storage`

Responsibilities:

- upload
- download
- remove
- list
- metadata
- signed URLs
- local development storage

Initial providers:

- local filesystem/dev adapter
- S3-compatible adapter

Portable APIs must avoid assuming a public bucket model.

---

## Payments

Package: `@onestack/payments`

Responsibilities:

- customers
- checkout
- subscriptions
- billing portal
- webhook verification/dispatch
- normalized payment events

Stripe is the first official provider adapter.

Stripe-specific functionality must remain behind the Stripe adapter when it cannot be represented portably.

All secret-key operations and webhook verification remain server-only.

---

## Deployment

Package: `@onestack/deploy`

Deployment uses provider presets rather than provider-specific application APIs.

Initial presets:

- Vercel
- Netlify
- Cloudflare
- generic Node
- Docker
- static export where compatible

CLI:

```bash
onestack deploy
onestack deploy --provider vercel
onestack deploy --provider netlify
onestack deploy --provider cloudflare
```

A deployment preset defines:

- build target
- output layout
- server/runtime mapping
- environment variable expectations
- static assets
- server functions
- deployment metadata

Application code must not need to change simply to switch deployment provider where capabilities overlap.

---

# Configuration

`onestack.config.ts` remains the primary configuration surface.

The existing `app` and `desktop` configuration remains valid.

New optional sections:

```ts
export default defineConfig({
  app: {},
  desktop: {},
  mobile: {},
  data: {},
  auth: {},
  storage: {},
  payments: {},
  deploy: {},
});
```

The configuration package should expose strict TypeScript interfaces without forcing provider packages into every application.

Provider adapters should be referenced through lightweight identifiers or lazy/imported configuration structures that preserve tree shaking.

---

# Server Boundary and Secrets

OneStack server functions remain the privileged execution boundary.

Sensitive service calls, including database writes requiring server credentials, privileged auth actions, payment actions, signed-storage operations, and webhook handling must execute through server-only code.

The compiler/build pipeline must prevent server-only secrets from being emitted into client, desktop renderer, or mobile application bundles.

CI should include a regression test that searches generated client artifacts for known test secret values.

---

# Universal Error Model

OneStack service/runtime failures should normalize into a shared error shape.

Conceptual fields:

- `code`
- `message`
- `cause`
- `provider`
- `retryable`
- optional structured metadata

Provider exceptions must be translated at adapter boundaries where possible.

Unsupported platform capabilities must fail explicitly.

There must be no silent fallback from native behavior to WebView or from a configured provider to another provider.

---

# Compatibility

v0.4 must preserve the v0.2 application model.

Requirements:

- existing web apps continue to build
- existing desktop apps continue to build
- existing `desktop` config remains valid
- old desktop compatibility config remains supported during migration
- all new configuration blocks are optional
- the existing counter example remains valid

Any unavoidable incompatible change requires an explicit migration path and must be documented.

---

# Testing Strategy

## Core tests

- renderer behavior
- signals integration
- routing integration
- mobile primitive mapping
- bridge request/response validation
- permission checks
- error normalization

## Adapter contract tests

Every adapter must pass the same provider-independent contract tests.

Examples:

- data adapter CRUD/transaction behavior
- auth session lifecycle
- storage upload/download/delete
- payments normalized event handling

## Platform CI

CI should cover:

- TypeScript tests
- TypeScript typecheck
- JS/package build
- existing Rust desktop checks/builds
- Windows desktop
- macOS desktop
- Linux desktop
- Android build
- iOS build on macOS runners

## Security regression tests

- no configured test secrets in generated client bundles
- native capability access denied when undeclared
- webhook signatures verified before dispatch
- unsafe provider config rejected

Required functionality:

# Definition of Done

OneStack v0.4 is complete only when all of the following are true:

1. Workspace build succeeds.
2. TypeScript typecheck succeeds.
3. Unit tests pass.
4. Existing web example still works.
5. Existing desktop example still works.
6. Android app can build and launch.
7. iOS app can build and launch.
8. Native mobile rendering works for the initial portable primitive set.
9. Explicit WebView fallback works.
10. Mobile capability permissions are enforced.
11. Data API works through SQLite and PostgreSQL adapters.
12. Auth API implements the documented portable session flows.
13. Storage API works through local and S3-compatible adapters.
14. Payments API works through the Stripe adapter.
15. Deployment presets produce valid provider output for the supported initial targets.
16. Service adapters pass shared contract tests.
17. Sensitive configuration is server-only.
18. Generated client/mobile bundles contain no test secrets.
19. A universal reference example demonstrates routing, auth, data, storage, and payments.
20. Documentation covers mobile, adapters, configuration, deployment, unsupported cases, and migration guidance.
21. CI validates web, desktop, Android, and iOS paths.

# Package Boundaries

To keep the project maintainable, implementation must avoid monolithic files/packages.

Major responsibilities should remain isolated behind explicit interfaces:

- renderers
- bridges
- provider contracts
- provider implementations
- CLI orchestration
- deployment presets
- service APIs

Consumers should not need to understand adapter internals to use the public API.

Internal implementations may change without breaking public contracts.

---

# Implementation Order

The implementation should proceed in this order:

1. shared mobile contracts and configuration
2. mobile renderer and bridge protocol
3. Android shell
4. iOS shell
5. mobile CLI orchestration
6. data adapter contracts and providers
7. auth contracts/providers
8. storage contracts/providers
9. payments contract and Stripe provider
10. deployment presets
11. universal example
12. cross-platform CI and security regression tests
13. documentation and migration notes

This order keeps each subsystem independently testable and minimizes coupling between unfinished layers.
